# 시안 3안이 서로 비슷했던 진짜 이유 — 계약이 다양성을 금지하고 있었다

## 지적

3사이클 산출물을 보고 사장이 말했다. *"디자인이 다 비슷비슷한데, 리서치 팀이 디자인 시안을 발굴을 안하나?"*

인상 비평으로 넘기지 않고 **측정했다**.

```
3사이클(꽃집)  a/b/c → 섹션 순서 hero → products → about → location → contact  (3안 완전 동일)
2사이클(베이커리) a/b/c → 같은 순서                                          (사이클을 넘어서도 동일)
```

**세 안이 다른 것은 팔레트·그리드 열 수·모서리 반경뿐이었다.** 골격은 하나였다.

## 원인 두 가지 — 순서가 중요하다

### 1. (더 근본) 계약이 레이아웃을 한 가지로 못박았다

계약에 이렇게 적혀 있었다.

> `sections` 5개(hero/products/about/location/contact)를 각각 `<section id="hero">` 처럼 **id 를 계약 이름 그대로** 달아 만든다.

그리고 이것이 **검수 5번 항목**이었다. 즉 **다르게 만들면 검수에서 떨어진다.**
제작자에게 "창의적으로 하라"고 아무리 말해도 소용없다 — **판정 기준이 획일을 강제하고 있었으므로.**

이 조항 자체는 이유가 있었다. 1사이클에서 필수 섹션이 통째로 빠지는 사고를 막으려던 것이다.
문제는 **"필수 콘텐츠가 있는가"(정당)** 와 **"정해진 순서로 5개여야 한다"(과잉)** 를 한 항목에 묶은 것이다.

> 교훈: **검수 항목은 "무엇이 있어야 하는가"만 말해야 한다. "어떻게 배치돼야 하는가"까지 말하는 순간 그 항목은 디자인을 결정해 버린다.**

### 2. 레퍼런스 발굴 단계가 아예 없었다

`in` 스테이지는 **소재만** 모았다. 스타일은 제작자가 **상상으로** 지었다.
근거 없이 지어내면 LLM 은 자기 기본값으로 수렴한다 — 그게 "AI티"의 정체다.
디자인 사업부 원칙에도 이미 있던 문장이다: **레퍼런스 실물 채집이 생성의 전제.**

## 처방 (계약 v4)

1. **`sections` 를 "필수 콘텐츠 집합"으로 강등.** 순서·분할·병합은 안별로 자유.
   검수는 *"상품 목록이 있는가 / 오시는 길 정보가 있는가"* 를 보고, **id 순서는 보지 않는다.**
2. **`archetype`(구조 원형)을 `styles.json` 의 1급 필드로.** 세 안이 팔레트뿐 아니라 **골격부터 달라야** 한다.
   예: 풀블리드 히어로 / 사이드바 고정 + 우측 스크롤 / 매거진 2단 / 리스트형 카탈로그.
3. **리서치 스테이지 신설** — 실제 웹에서 레이아웃 패턴을 채집해 `01_brief/refs.json` 으로 남긴다.
   **시각 패턴만 가져오고 코드·에셋·문구는 가져오지 않는다.** 레퍼런스는 방향이지 원본이 아니다.
4. **검수에 "구조 상이성" 항목 추가** — 세 안의 섹션 구성·그리드·히어로 유형이 **서로 달라야 통과**.
   지금까지는 팔레트 상이만 봤다(9번). 그래서 색만 다른 세 쌍둥이가 통과했다.

## 이 실패가 말해주는 것

[[검수가_잡아낸_것들]] 은 검수가 **막아낸** 것을 모은다. 이 문서는 반대다 — **검수가 만들어낸 결함**이다.
자동 판정을 붙이면 산출물은 **판정 기준을 향해 수렴한다.** 기준이 곧 설계가 된다.
그러므로 계약을 쓸 때 물어야 할 질문은 *"이걸로 불량을 걸러낼 수 있는가"* 만이 아니라
**"이 기준이 통과시키는 것들이 서로 얼마나 다를 수 있는가"** 이다.
